# Testing

Three suites, in order of how fast they fail and how much they need.

| Suite | Command | Needs | Count | Runtime |
|---|---|---|---|---|
| Unit | `npm test` | nothing | 290 | ~4s |
| Integration | `npm run test:integration` | Postgres | 144 | ~25s |
| End-to-end | `npm run test:e2e` | Postgres + a running server + Chromium | 45 checks | ~90s |

`npm run test:all` runs the first two. CI (`.github/workflows/ci.yml`) runs all
three on every push, in three parallel jobs.

## Unit — `tests/*.test.ts`

Pure functions only: streak arithmetic, day-key math, leaderboard ranking,
plan catalogs, payoff simulation, launch-readiness checks. No database, no
mocking beyond the occasional Prisma stub, no framework. If a change breaks
one of these it's a logic error, and it'll tell you in four seconds.

## Integration — `tests/integration/*.test.ts`

Real Postgres, real Prisma, real route handlers.

**Why not mock Prisma.** Mocking it proves a function *called* the database.
For interest accrual, plan limits and permission checks, whether the *query*
is right is the entire question — and a mock will happily agree with a wrong
one. These run against a throwaway database instead.

**How authentication works.** Route handlers are plain functions, so there's
no HTTP server here. `lib/auth.ts` accepts an `Authorization: Bearer fw_pat_…`
API token as well as a session cookie, so `factories.ts` mints a real
`ApiToken` per test user and requests authenticate through exactly the code
path production uses. The only thing stubbed is Next's request scope
(`tests/integration/nextContext.ts`), because `cookies()` throws outside one.

**The database.** `TEST_DATABASE_URL`, defaulting to a local
`debtsucker_test`. `globalSetup.ts` creates and migrates it once per run
(`prisma db push`, so a schema change is testable before its migration is
written); every file truncates it in `beforeEach`. Files run sequentially —
they share one database.

What's covered:

- `money.test.ts` — loans, payments, overpayment, interest accrual and its
  same-month idempotence, goal contributions
- `billing.test.ts` — the Stripe webhook, with signatures generated by
  Stripe's own library so a wrong secret or a tampered body really fails
- `permissions.test.ts` — all 34 household routes swept for 401 on anonymous,
  403 on non-member, plus cross-household id confusion
- `validation.test.ts` — malformed bodies, out-of-range values, unknown enum
  members, and plan limits at the exact boundary
- `scale.test.ts` — a 12-member household with two years of chore history
- `concurrency.test.ts` — genuinely parallel requests (`Promise.all`, not
  sequential awaits)

## End-to-end — `tests/e2e/launch.mjs`

A real browser through everything a new user does on day one: the public
pages, signup, household creation, chores, invite-and-accept, loans, goals,
the Today panel, billing, logout/login, the mobile layouts. Also sweeps for
duplicate element ids and unlabelled form fields.

```bash
npm run dev                                       # one terminal
npm run test:e2e                                  # another
BASE_URL=https://staging.example npm run test:e2e # or against a deploy
```

It creates throwaway accounts, so point it at staging rather than production.

Every assertion polls rather than sleeping. Fixed timeouts made this suite
flaky three separate times during its own construction — each one looked like
a product bug and wasn't. If you add a check, wait for the condition.

## Writing a new test

**Testing a pure function?** `tests/`. **Testing a route, a query, or
anything that touches the database?** `tests/integration/`, using the
factories:

```ts
const owner = await makeUser();
const member = await makeUser();
const hid = (await makeHousehold(owner, [member])).id;

const res = await call(POST, `/api/households/${hid}/chores`, { hid }, {
  as: owner, body: { name: "Dishes" },
});
expect(res.status).toBe(200);
expect(await db.chore.count()).toBe(1); // read the database back, not the response
```

Assert against the database, not just the response body. A route that returns
the right JSON while writing the wrong row is the failure mode that costs
money, and it's invisible if you only check what came back.

**Adding a household route?** Add it to the `ROUTES` table in
`permissions.test.ts`. The list is explicit so that forgetting is visible in
review rather than silent.

## Two bugs this suite found

Both were concurrency bugs in money paths, both invisible to sequential tests:

1. **Goal contributions lost money.** The contribute route read
   `currentAmount`, added to it in JavaScript, and wrote the result back. Two
   people funding the same goal at the same moment — the normal case, not an
   exotic one — both read the same starting value, and the second write
   discarded the first person's contribution. Five parallel contributions
   totalling $150 landed as $30. Now an atomic `increment`.

2. **The daily bonus paid twice.** `maybeAwardDailyBonus` checked "has this
   user been paid today?" and then paid, with a gap in between. Racing the
   third objective paid the bonus twice — 30 Crowns and 20 XP instead of 15
   and 10. Now it claims the day first by inserting the keyed notification
   (whose `(userId, key)` unique constraint is the mutex) and only pays if it
   won.
